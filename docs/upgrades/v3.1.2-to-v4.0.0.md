# Upgrade from v3.1.2 to v4.0.0

v4.0.0 is a breaking template release. It removes unused default surfaces,
archives legacy providers, narrows the default locale build to English, and
tightens authentication, storage, payment, environment, and tooling contracts.
It does not update a downstream repository, migrate its database, rewrite R2
keys, or configure external providers automatically.

Adopt this release on a dedicated downstream branch. Keep the last deployed
commit, a database backup, and an R2 inventory before changing code. Existing
products keep their product-owned migration ledger; do not copy or renumber the
template's historical migrations into an established product.

## Breaking changes to assess first

- The reusable `apps/web/src/components/listing` implementation was removed.
  Products importing it must retain their product-owned copy or migrate those
  screens to the remaining UI primitives before accepting the deletion.
- Aliyun phone login, Aliyun OSS, Creem, and Waffo integrations are no longer
  active template providers. Their source and recovery notes remain under
  `archive/`; products that use one of them must preserve their implementation
  and configuration during the merge.
- The active i18n package builds English only. The former Chinese and Japanese
  catalogs remain under `packages/i18n-dormant-catalogs/` or its archived
  location in repositories that already adopted the cleanup. A multilingual
  product must restore its product-owned catalogs and locale configuration
  rather than replacing them with the English-only default.
- Production configuration now fails early when an enabled module is missing a
  required secret. Review Stripe, RevenueCat, Resend, Turnstile, auth, R2, Web
  URL, and Server URL values before deployment.
- Browser-exposed `VITE_*` values use an explicit allowlist. Product-specific
  public variables must be deliberately added to the public configuration
  contract; server secrets must never be added to that list.
- Authentication redirects accept only same-origin relative destinations.
  Custom sign-in links should use a relative `redirectTo` or `returnTo` value.
- Storage records now enforce resource ownership. Historical assets need a
  reviewed ownership backfill before owner-scoped operations are enabled for
  existing data. Existing R2 object keys are not rewritten.
- Payment recovery, refund/dispute visibility, dead-letter administration, and
  purchase-history pagination changed. Products with live billing must validate
  their Stripe and RevenueCat webhook scenarios in provider sandboxes.
- Product profiles and auto-merge configuration now have one authoritative
  source. Preserve product choices in the supported profile inputs instead of
  editing generated outputs.

Fumadocs, Orama, blog support, and the design-system gallery remain available.
The template ships without documentation MDX by default, so `/docs` can return
404 until the product adds documentation content.

## Recommended adoption sequence

1. Create an upgrade branch from the downstream production branch and record
   the current deployed commit.
2. Back up the downstream database and record current R2 keys, enabled modules,
   locales, provider integrations, and required environment variables.
3. Compare `v3.1.2...v4.0.0` and preserve downstream-owned provider, listing,
   locale, branding, content, and migration files before resolving deletions.
4. Merge or cherry-pick the reviewed runtime and tooling changes. Do not replace
   the downstream migration ledger with the template ledger.
5. Apply any required schema additions as the downstream product's next normal
   migration. Rehearse ownership backfill and rollback on a database copy.
6. Update production configuration and secrets for every enabled module. Keep
   disabled modules disabled instead of supplying fake production credentials.
7. Restore product-owned Chinese/Japanese catalogs or archived providers only
   when that downstream product actually uses them.
8. Run the downstream checks, then exercise authentication, uploads, billing,
   webhook replay, refunds, disputes, email, and public forms in staging.
9. Deploy the database and server in the product's documented order, then the
   Web application. Observe error rates and payment dead letters before
   promoting the release.

## Minimum downstream checks

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm check-types
pnpm test
pnpm build
pnpm template:upgrade-check
```

Run `pnpm mobile:check` when the downstream includes the optional mobile app.
Run provider sandbox checks only with non-production credentials. Never use a
real payment, production migration, or live email send as a smoke test.

## Rollback

The source rollback point is the downstream commit recorded before adoption.
Re-deploy that commit if the application rollout fails. Database changes need a
forward correction or a separately reviewed restore from backup; reverting code
does not undo an applied migration or ownership backfill. Do not delete new R2
objects or payment/audit records as part of an automatic rollback.

The upstream template retains the reviewed pre-release and tested snapshots, and
legacy provider source remains in `archive/`, so code can be recovered without
rewriting downstream history.

## Release acceptance checklist

- No unresolved imports from the removed listing package remain.
- Every retained legacy provider has an explicit downstream owner.
- Required locales compile and locale URLs resolve as intended.
- Enabled modules have real staging configuration and disabled modules need no
  placeholder secrets.
- Historical assets have an ownership migration decision and rollback record.
- Stripe and RevenueCat sandbox scenarios pass for the product's enabled flows.
- Cloudflare WAF, Turnstile, R2, Resend, and allowed origins match the target
  environment.
- The full downstream test and build commands pass before production promotion.
