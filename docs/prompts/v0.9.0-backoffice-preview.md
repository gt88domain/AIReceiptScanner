# v0.9.0 执行 Prompt：Backoffice 预览环境与人工验收

> 用法：把本文件整段交给执行编码的 AI（或自己照做）。
> 本版本只回答一个问题：**现有 User / Admin 后台到底是不是我们想要的**。
> 本版本不加任何新产品功能。

## 背景（只读，不要改动其中提到的外部系统）

- 仓库：上游模版 `tanstack-template`（当前 main = v0.8.0 / cd53c54）。
- 已完成：Admin A（Overview / Users / Integrations / Audit / System）、Admin B（Analytics）、ControlReadV1、ControlRead transports。
- 已有用户侧页面：`/dashboard`、`/settings/profile`、`/settings/security`、`/settings/billing`、`/credits/purchase`、`/credits/transactions`。
- 已有 capability / product profile 机制：`packages/app-config/src/profile-definitions.ts`（`full-saas` / `account-app` / `directory` / `directory-lite`）。
- 问题：上游默认启用 email verification、Resend、Billing、Credits，本地启动**不能**一键注册并验收后台。
- 本版本目标：补一个隔离的 `preview:backoffice` 工作流，让任何人（尤其非技术验收者）一条命令启动后，能登录普通用户和管理员两个账号，逐页验收全部后台页面。

## 目标

新增 `pnpm preview:backoffice`，满足：

1. 使用**本地 D1**，绝不触碰生产 D1 / 生产 Worker / 任何真实 provider。
2. 不调用 Resend（邮件验证在预览模式下关闭或打桩）、不调用 Stripe / Creem / 任何支付 provider、不初始化 Queue / R2。
3. 自动准备两个本地账号：
   - 普通用户：`user-preview@local.test`
   - 管理员：`admin-preview@local.test`（邮箱加入预览模式的 `ADMIN_EMAILS`）
   - 两个账号只存在于本机 local D1，固定密码写在终端输出里，仅供本机使用。
4. 启动后终端打印验收清单链接：
   - 用户侧：`/dashboard`、`/settings/profile`、`/settings/security`、`/settings/billing`、`/credits/purchase`、`/credits/transactions`
   - 管理员侧：`/admin`、`/admin/analytics`、`/admin/users`、`/admin/integrations`、`/admin/audit`、`/admin/system`
5. Billing / Credits 相关页面在预览中的显隐必须遵循现有 capability / profile 机制（先确认用哪个 profile 预览，推荐 `full-saas` 用于验收全部页面；如技术上更简单，可用 `account-app` 并在输出中说明哪些页面因此不显示）。

## 实现要求

- 新增脚本与种子代码放在合适位置（如 `scripts/` 或 `apps/server` 的本地工具区），**不要**把预览逻辑塞进生产运行时路径。
- 种子逻辑幂等：重复执行 `preview:backoffice` 不产生重复账号、不报错。
- 预览模式通过显式环境变量开启（如 `BACKOFFICE_PREVIEW=1`），生产部署路径必须完全不受其影响；在 `.env.development.example` 增加对应说明。
- 预览模式的安全边界：
  - `BACKOFFICE_PREVIEW=1` 时若检测到生产环境标识（生产 D1 / 生产 Worker 配置），直接拒绝启动并报错。
  - 预览种子账号密码只允许写入本地终端输出，不写入任何会被提交的文件。
- 文档：在 `docs/` 增加一页「Backoffice 预览与人工验收」说明（如何启动、两个账号、验收清单、常见问题）。

## 明确不做（Non-goals）

- 不新增、不重构任何后台页面功能；验收中发现的体验问题只记录到验收清单结果里，留待 v1.0 决策。
- 不改 User / Admin 信息架构、不改导航命名。
- 不做 Tickets、Apps、Modules 扩展点。
- 不动 Central（aibranding-control）仓库，不动任何下游项目。
- 不配置生产 Zero Trust。
- 不运行 `git clean -fd`；不触碰无关的未跟踪文件（如 `docs/multi-repo-map.md`）。

## 测试与门槛

- `pnpm test`（template + integration）全绿。
- 为种子/预览守卫加最小聚焦测试：预览模式在检测到生产配置时 fail-closed。
- `pnpm check-types` 通过。
- 提交遵循 Conventional Commits，建议拆分：
  1. `feat(preview): add backoffice preview workflow`
  2. `docs(preview): document backoffice acceptance flow`

## 验收出口（人工，由项目所有者执行）

执行者完成开发后，项目所有者：

1. 运行 `pnpm preview:backoffice`。
2. 用两个账号分别登录，逐页点完 12 个页面。
3. 按 `docs/prompts/v0.9.0-acceptance-checklist.md`（执行者需一并生成该模板）逐页记录：可用 / 有问题 / 缺什么。
4. 验收结果作为 v1.0.0（用户侧 IA 定稿）的输入。

## 完成定义（Definition of Done）

- [ ] `pnpm preview:backoffice` 一条命令可启动完整预览
- [ ] 普通用户与管理员账号均可登录，权限隔离正确（普通用户访问 `/admin/*` 被拒）
- [ ] 无任何外部 provider 调用，本地 D1 可重复种子
- [ ] 生产 fail-closed 守卫有测试
- [ ] `pnpm test` 与 `pnpm check-types` 全绿
- [ ] 验收清单模板已生成，预览启动输出包含全部 12 个页面链接
