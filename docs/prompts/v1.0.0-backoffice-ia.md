# v1.0.0 执行 Prompt：User + Admin 后台信息架构定稿

> 用法：把本文件整段交给执行编码的 AI。
> 前置：v0.9.0（`pnpm preview:backoffice` 预览工作流）必须先成为独立的本地 checkpoint commit；
> 在它尚未合入 `main`（当前 main 仍在 v0.8.0）期间，本版本仍须在独立分支（如 `codex/backoffice-ia-v1`）上实施。
> 如果 v0.9.0 仍有未提交改动，先停止，不得与 v1.0.0 混合；v1.0.0 完成后停在未提交状态等审查。
> 本版本目标：把「目标 IA + 显隐规则」落地，让后台成为真正每天可用的用户中心与运营面板。
> 本版本不做任何项目专有功能、不动 Central。

## 背景

- 仓库：上游模版 `tanstack-template`。
- v0.9.0 人工验收结论：路由、权限、六个 Admin 页面都能跑，但用户侧缺工作流、管理侧像内部技术面板。
- 本 prompt 附有所有者已签字的产品决策，**不要重新讨论已定的决策**，有异议只在 PR 描述中注明。
- 实施前必须先读 `packages/app-config/src/features.ts` 与 `profile-definitions.ts`，
  以现有旗标为准；本 prompt 中的显隐条件均已映射到现有旗标。

## 已签字的产品决策（约束，不得违背）

1. 目标 IA 不等于默认可见：每个导航项由现有 capability / features 旗标显隐，新项目第一天只看到最小导航。
2. 管理侧不做 Cloudflare / Stripe Dashboard 的低配复制品：不自建流量/性能 Observability；退款、争议、税务一律深链支付商后台；自己只保留「是否配置、最后成功时间、失败原因、需不需要处理」，绝不显示 secret、provider identifier、binding identifier。
3. 管理侧新增页面全部只读。
4. Saved（收藏）、Rewards / Redeem 已从计划中移除，本版本不做。
5. Tickets 是 v1.1 的 capability 模块，本版本不做，**也不预留任何 tickets 开关或分支**（当前 features 中没有该旗标，禁止新增永远关闭的开关）。
6. 不伪造数据：页面上每个字段必须来自现有真实 read model；没有数据来源的就不显示。

## 范围 A：用户侧 IA

目标导航（括号内为显隐条件，均映射到 `features.ts` 现有旗标）：

```
Dashboard                      全部项目，永远显示
Purchases                      web.billing 或 web.creditPurchases 任一开启
Account
├─ Profile                     永远显示
├─ Security                    永远显示
├─ Billing                     web.billing 开启
└─ Credits                     web.credits 开启
Help                           永远显示（极简联系页，复用现有 Contact 链路）
```

（Apps 分组本期不做页面、不做机制，v1.2 才引入；导航代码中不留空壳。）

具体工作：

1. 现有 `Settings` 导航分组改名为 `Account`，四个子页面（Profile / Security / Billing / Credits）路径可保持不变，仅改导航与标题文案；i18n messages 同步更新。
2. 显隐规则全部走现有 `packages/app-config` features 机制，**不得新增任何特性开关**：
   - Billing：`web.billing` 开启才显示。
   - Credits：`web.credits` 开启才显示。
   - Purchases：`web.billing || web.creditPurchases` 开启才显示。Purchases 为用户侧新页面：只读列出当前用户的订单/购买记录（类型、金额、状态、时间），数据来自现有支付 read model；无订单时显示空状态。
3. Dashboard 定位为通用摘要页：账户状态卡 + 各已显示导航项的快捷入口。不做项目定制内容。
4. Help 为极简联系页：**复用现有 Contact 邮件链路**（`apps/server/src/handlers/contact.ts`，服务端 `CONTACT_RECIPIENT`）；`CONTACT_RECIPIENT` 未配置时显示 mailto 兜底。**不建 Help Center 内容库、不做 FAQ 系统。** 预览模式下与既有预览阻断行为保持一致（当前实现为 503；如统一调整为 403，需在 PR 中说明并同步更新相关测试）。
5. 用户侧不需要也不允许出现：Saved / Favorites / Rewards。

## 范围 B：管理侧 IA

目标导航：

```
Overview        待处理导向（见下）
Users           已有，不动
Payments        web.billing 或 web.creditPurchases 开启时显示；只读
Analytics       已有，不动
Audit           已有，不动
System          并入原 Integrations 内容
```

具体工作：

1. **Integrations 并入 System**：System 页新增 `Providers` 区块，承载原 Integrations 全部内容（D1 / R2 / Queue / OAuth / 支付 / 邮件等 provider 的 configured / disabled / missing 状态）；删除顶层 Integrations 导航与路由，原 `/admin/integrations` 重定向到 `/admin/system`。保持既有不变量：不暴露 secret、provider identifier、binding identifier。
2. **Overview 改为最小待办队列**，只保留以下来源，全部只读 + 深链，且每项数据必须来自现有真实 read model：
   - 失败 / dead-lettered Webhook 数量（有支付能力时）
   - 失败支付数量 → 深链本版 Payments 页（有支付能力时）
   - runtime / 模版版本与**已应用 migration 状态**（复用 System 已有数据；当前没有可信的「最近部署记录」，禁止伪造部署时间）
   - 不做告警规则引擎、不做写操作、不做 Tickets 卡片（v1.1 再加）。
3. **Payments 新页面**（有支付能力时显示）：只读订单/订阅列表 + 失败原因。**深链规则：只有 read model 中已存在安全、配置化的支付商外部 URL 时才显示到对应记录的深链；否则只提供支付商 Dashboard 首页链接。禁止猜测拼接 Stripe / Creem 单据 URL，禁止泄露 provider identifier。** 不做退款、不做争议处理、不做任何写操作。

## 显隐矩阵（本版本的验收基准，写进 docs）

用户侧：Profile / Security / Dashboard / Help = 必选；Billing = `web.billing`；Credits = `web.credits`；Purchases = `web.billing || web.creditPurchases`；Apps = v1.2；Tickets 入口 = v1.1。

管理侧：Overview / Users / Analytics / Audit / System = 必选；Payments = `web.billing || web.creditPurchases`；Support = v1.1；项目专有 Modules = v1.2。

永久不做（写入路线图文档）：不自建 Observability；不做退款/争议/税务 UI；不做匿名收藏；不做运行时插件；不做 Central 相关改动；不伪造数据来源。

## 明确不做（Non-goals)

- 不做 Tickets 及其任何开关、分支、卡片。
- 不做 Help Center 内容库、FAQ。
- 不做 Saved / Rewards / 用户侧 Apps 页面本体。
- 不做项目专有管理页（Domains 等），那是 v1.2。
- 不改 `/dashboard` 等现有路由路径（只改导航/标题/分组），避免破坏下游书签与测试。
- 不修改头像安全策略；已知的 avatar 集成测试失败是既有问题：如确认是旧测试期望与安全策略不符，允许在**独立 commit** 中更新该测试期望；不确定则原样保留并在 PR 中说明。
- 不动 Central 仓库与任何下游项目。

## 测试与门槛

- 显隐规则必须有聚焦测试：每个旗标组合下导航项出现/消失（至少覆盖 directory-lite、account-app、full-saas 三个 profile）。
- Integrations 并入 System 后：原有「不泄露 secret」的测试必须仍然通过或等价迁移。
- Payments 页与 Overview 待办数据：只读 read model 测试（空态、有失败记录、无支付能力时隐藏）。
- Help 表单：预览模式阻断的测试（状态码与既有实现一致）；正常模式走既有 Contact 邮件路径的 mock 测试。
- `pnpm test` 全绿（avatar 既有失败按上面规则处理）、`pnpm check-types` 通过、`pnpm lint` / `pnpm fmt:check` 通过。

## 验收出口（人工，项目所有者执行）

1. `pnpm preview:backoffice` 启动，用管理员与普通账号分别核对新导航与显隐。
2. 用 profile 切换（directory-lite / account-app / full-saas）核对显隐矩阵。
3. 对照 `docs/prompts/v0.9.0-acceptance-checklist.md` 更新版逐页签字。
